# SUAS 2027 training environments

The owner supplied **SUAS_2027_Primer_and_Task_Ideas.pdf**, titled *SUAS 2027 — Primer & Task Ideas*.
This is the source used here; it is not copied into the public repo. Page numbers below count the PDF
cover as page 1. No final Team Handbook, landing-zone definition, scoring formula or report JSON schema
was supplied. This guide records the brief without inventing missing competition rules.

The 2026 runway demo and real-drone code keep their current behavior. The new `challenge2027` modules
and Blender tools create a **separate perception/terrain sandbox**, not an autonomous 2027 mission brain.
The coastal setting is fictional; it does not claim to recreate the real Skyway Range shoreline.

## Repeatable challenge cases

Every random choice comes from `--seed`; cases have separate output folders and world names. Reuse a seed
across cases for a paired comparison. Use different held-out seeds for evaluation, not near-duplicate
views from the training scene. These are **designed stressors**, not measured image visibility labels.

| `--case` | Change | Evidence to collect from a real model |
|---|---|---|
| `baseline` | Distinct clothing, relief, clutter, bystanders with luggage, clearings and harbor | Hiker localization; three color attributes; suitcase association; valid/nearest clearing. |
| `occluded` | A bush overlaps the hiker | Miss rate and localization drift against the paired baseline. Actual pixel occlusion fraction is not labeled. |
| `low_contrast` | Green shirt, brown pants, black suitcase | Color confusion and recall against terrain/background; no prescribed contrast metric. |
| `low_sun` | Sun elevation 12 degrees instead of 52 | Shadow robustness; compare the actual Gazebo camera as well as the Blender preview. |
| `negative` | No stranded hiker or associated suitcase; bystanders/clutter remain | Hiker false alarms and abstention. This deliberate negative is an engineering test, not a claim the mission has no hiker. |

The search area has no painted candidate labels or answer markers. The public `task.json` describes the
search rectangle and candidate geometry without validity, colors or the target position. `scene.json`
is the **private answer key**; never provide it to the model under test. Likewise, do not use the optional
truth detector to measure the new perception challenges: it bypasses color recognition and occlusion.

## Build with Blender

Blender is needed **offline to generate the assets**, not on the Jetson or during Gazebo flight. The
generator uses original procedural geometry and a procedural albedo image: no downloaded people, GIS
imagery, external textures or model weights. Generated `.blend`, PNG and mesh outputs stay outside Git.
Blender 5.2.3 was used for the first export. Earlier Blender versions are not yet tested.

Run these Linux commands from the **Linux-side checkout**, after the normal
[build/setup](../../simulation/README.md). Serialize generation with builds, Docker and simulator jobs.
On the shared WSL laptop, acquire the heavy-job lock first (see `LOCAL_NOTES.md`).

```bash
source simulation/setup/sim_env.sh
python3 ros2_ws/src/simulation/sim_worlds/scripts/build_suas_2027.py \
  --case baseline --seed 2027 --blender blender \
  --out-dir "$HOME/.astra_sim/world_data/suas2027/baseline_2027" --preview
```

`--blender` is the executable path, not its installation directory. For Blender installed on Windows,
use its WSL-mounted `blender.exe` path as that argument. The wrapper translates the Python script,
recipe and output paths for the Windows process; machine paths belong in local notes only. Run Linux
commands through a `.sh` file from PowerShell, as the local notes explain.

The Blender-only geometry regression runs separately from ROS pytest, using the same executable:

```bash
blender --background --factory-startup --threads 4 --python-exit-code 1 \
  --python ros2_ws/src/simulation/sim_worlds/test/blender_geometry_smoke.py
```

Its four human poses must retain metre-scale bodies and export their shirt/pants materials. This catches
Blender's deferred-transform trap: copying `matrix_world` before an update can inflate the last boot.

Use `--recipe-only` to inspect a cheap scene recipe without launching Blender. `--assemble-only` rebuilds
SDF/config/truth/mission around already exported geometry of that same seed/case. A nonempty unrelated
output directory is refused. Changing the seed or case requires a separate output directory.

Expected bundle:

```text
scene.blend                       editable terrain, people, props and optional preview cameras
scene.json                        private answer key and complete scene recipe
task.json                         public search area and candidate geometry; no target answers
assets.json                       Blender version, triangle totals, materials, measured hiker bounds
bundle.json                       relative files, search acreage and conservative survey clearance
overview.png                      optional overview
hiker_50m.png                     optional 2560 x 1440 / 81-degree HFOV / 50 m AGL camera image
hiker_detail.png                  optional close inspection; not a flight-height detection benchmark
models/<world>/                   model.sdf, model.config, meshes and exported albedo
worlds/<world>.sdf                 Gazebo shell with the existing systems/home convention
config/<world>.yaml                portable external world configuration
truth/<world>.yaml                 legacy-shaped hiker positions for visualization, no invented tent
missions/<world>_survey.waypoints  QGC WPL 110 survey in the existing index shape
```

The generator budgets **500,000 visual triangles**. Terrain visual and physics reference the **same
51,200-triangle OBJ**, with height lookup interpolating those exact triangles. Tree trunks, buildings,
vehicles and wires have separate cheap collision shapes. Foliage, small props and the mannequin are
visuals rather than complete physical models. Water has no buoyancy or wave simulation. A geometric
wire alone does not prove a small moving vehicle will detect or collide with it reliably.

The ground has a flat origin for takeoff. Survey altitudes are **above home**, chosen to leave at least
50 m above the highest terrain vertex. Lanes use the smallest ground clearance for conservative
sidelap, unlike applying an above-home height directly to every local footprint. A later invocation
of the old `make_mission.py` does not preserve this special terrain treatment; regenerate with the
2027 builder instead. Terrain, props and camera views still need live performance/physics validation.

The [Gazebo mesh guide](https://gazebosim.org/api/sim/9/model_and_optimize_meshes.html) explains visual
versus collision geometry; [Harmonic's feature table](https://gazebosim.org/docs/harmonic/comparison/)
lists OBJ and COLLADA support. The exporter uses Blender's
[evaluated triangle mesh API](https://docs.blender.org/api/current/bpy.types.Mesh.html).

## Open the scene in Gazebo

Keep the bundle on a Linux filesystem for loading. If Windows Blender wrote to a mounted Windows drive,
copy the completed output to the Linux cache first. Then:

```bash
bundle="$HOME/.astra_sim/world_data/suas2027/baseline_2027"
export GZ_SIM_RESOURCE_PATH="$bundle/models:${GZ_SIM_RESOURCE_PATH:-}"
bash simulation/scripts/start_sim.sh "$bundle/config/suas2027_baseline_2027.yaml" panel:=false
# In a second terminal, open the current ground station:
bash simulation/scripts/mission_planner.sh start
# When finished:
bash simulation/scripts/stop_sim.sh
```

**Mission Planner with the ASTRA plugin is the operator interface**, as documented in
[MISSION_PLANNER.md](MISSION_PLANNER.md). The old Python/Qt demo panel is retired from this workflow:
keep `panel:=false` above and omit `--panel` when using `demo.sh` (`--no-panel` makes this explicit).
The autopilot remains ArduCopter SITL; selecting the ground-station window does not replace it.

A bounded **visible** integration check starts and stops its own Gazebo window/server, renders three
actual camera views and drops spheres at the origin, a clearing and the sloped candidate:

```bash
python3 ros2_ws/src/simulation/sim_worlds/scripts/check_suas_2027.py --bundle "$bundle"
```

The bundle's `checks/` folder receives `gazebo_check.json`, server/window logs and the three images.
The check requires all camera frames, no server errors, real-time factor at least 0.8 and each sphere's
resting center within 5 cm of the terrain surface plus its radius.
The launch slab is visual only; its physics surface is the underlying flat terrain. The check uses a
separate Gazebo partition and stops only the processes it created. The explicit `--no-gui`
option is for unattended CI; local validation uses the visible default.

This is a scene/simulator launch, not an automatic 2027 mission. The existing controller has no color
description, suitcase association, map production or helicopter landing-zone decision. Its fixed 49 m
drop height is above **home**, so it can fall below 150 ft **AGL** on this terrain. Do not claim a compliant
2027 delivery by running the old demo. The existing truth validator/scorer expects a person and a tent;
those 2026 assumptions remain unchanged. Use the independent diagnostics below for the new benchmark.

## Local report diagnostics

Use ordinary Python with the built environment. There is deliberately **no combined score** and no
invented hiker-location acceptance radius. This report schema is only for this repo's offline tests.
Coordinates are **local east/north metres**, not latitude/longitude. A report may explicitly set `hiker`
to `null` when no hiker is found; omitted attributes and unmeasured altitude stay unknown.

```json
{
  "schema": "astra.suas2027.report.v1",
  "hiker": {"x": 80.0, "y": 120.0,
            "shirt_color": "red", "pants_color": "blue", "suitcase_color": "yellow"},
  "landing_zone_id": "clearing_near",
  "delivery": {"x": 82.0, "y": 121.0, "release_agl_m": 50.0},
  "elapsed_s": 900.0
}
```

These numbers are an illustrative result, **not the answer to seed 2027**. `delivery.x/y` is the final
payload position. Evaluate a result kept outside the repo:

```bash
python3 -m sim_worlds.challenge2027.evaluate "$bundle/scene.json" result.json --out diagnostics.json
python3 -m pytest -q -p no:cacheprovider ros2_ws/src/simulation/sim_worlds/test
python3 simulation/scripts/check_docs.py
```

Diagnostics distinguish location error, each color match, missed targets/false alarms, selected-zone
validity, nearest valid zone (including ties), drop distance, reported release AGL and elapsed time.
Missing altitude cannot pass the altitude check. Retardant/survival and mapping quality remain explicitly
unverified. A successful CLI exit means the report was parsed; inspect the metrics to judge its result.
